Agent 提供两种调用方式：

对比项 invoke() stream()
返回方式 一次性返回最终结果 逐步输出中间状态

适用场景 只需要最终结果 需要实时监控 / 打字机效果 / 调试
用户体验 等待后一次性展示 实时渐进展示

二、values 模式：完整状态输出

2.1 工作原理

stream_mode="values" 模式下，每个步骤执行后，都会输出完整的状态信息。

状态是累加的——每一步的输出都包含从头到尾的所有消息。

2.2 完整代码

2.3 输出详解

关键特点：

  • 每次 chunk 都包含从头到尾的所有消息
  • 数据量逐渐增大（因为消息在累加）
  • 最后一个 chunk 包含完整的最终状态，等价于 invoke() 的返回值

2.4 适用场景

场景 说明
状态持久化 每步都需要保存完整状态到数据库
断点恢复 需要从任意步骤恢复执行
完整审计 需要记录每一步的完整对话历史
简单场景 不关心增量变化，只关心每步的完整快照

三、updates 模式：增量更新输出

3.1 工作原理

stream_mode="updates" 是默认模式。每个步骤执行后，只增量更新状态中发生变化的内容。

输出以节点名称为 key，值为该节点产生的变化。

3.2 完整代码

3.3 输出详解

关键特点：

  • 每次只输出当前步骤新增的内容
  • 以节点名称（agent / tools）为 key
  • 数据量恒定（不包含历史消息）
  • 更节省带宽和内存

3.4 values vs updates 对比

对比项 values updates
数据量 逐渐增大 恒定
包含历史 是 否
节点信息 无 有（agent / tools）
带宽消耗 高 低
适合持久化 是 否
适合监控进度 可以 最适合

四、messages 模式：流式 Token 输出

4.1 工作原理

stream_mode="messages" 模式输出流式返回的 Token 以及相关元数据（如来自哪个节点）。

这是粒度最细的模式——不是按步骤输出，而是按每个 Token 输出。

可以用在实现类似 ChatGPT 的打字机效果场景，为聊天机器人等交互式应用提供最佳的实时体验。

  • 逐 Token 输出，实现打字机效果
  • 每个 chunk 是 (消息对象, 元数据) 元组
  • chunk[0].content 是本次的 token 文本（可能只是一个字或几个字）
  • 粒度最细，实时性最强

五、tasks 模式：任务生命周期

5.1 工作原理

stream_mode="tasks" 模式输出当前 task 任务开始和结束的时间，包含任务的结果和错误信息。

用于监控任务的生命周期——每个工具调用被视为一个 task，可以看到它的 start 和 end 事件。

六、debug 模式：详细调试信息

6.1 工作原理

stream_mode="debug" 模式与 tasks 模式类似，但比 tasks 模式多输出任务步骤、时间戳、task 类型（task / task_result）。

用于调试、监控 task 任务的生命周期。

七、custom 模式：自定义数据流

7.1 工作原理

stream_mode="custom" 模式允许开发者通过 get_stream_writer 在工具或节点内部自定义发送的数据。

用于输出业务逻辑相关的进度信息（如”已处理10/100条记录”）、自定义日志或指标。

核心要点：custom 模式不会自动输出任何内容，只有当开发者在工具内部主动调用 writer() 时才会产生输出。
